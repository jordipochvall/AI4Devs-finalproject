# HU-38 — Las contraseñas de las cuentas semilla del demo se configuran por entorno

> **Como** equipo de plataforma,
> **quiero** que las contraseñas de las cuentas semilla (admin/operador/matemático/jugadores) se puedan fijar por variable de entorno en vez de venir escritas en el código,
> **para** que el VPS público no acabe con `admin123`/`operator123`/`player123` conocidas por cualquiera, sin dejar de tener cuentas de demostración listas para que un evaluador entre a probar la app.

**Prioridad:** Should Have · **Estimación:** S · **Perfil:** Plataforma/DevOps

## Contexto y valor

`SeedDataLoader` (`ApplicationRunner`, sin guarda de perfil — sólo se salta si `users` ya tiene filas) siembra 6 cuentas con contraseñas **literales en el código**: `admin@nova.test/admin123`, `operator@nova.test/operator123`, `math@nova.test/math123`, `player{1,2,3}@nova.test/player123`. Además, `scripts/smoke-test.sh` **depende** de poder iniciar sesión como `player1@nova.test/player123`, así que quitar el sembrado por completo rompería el propio *smoke test* del despliegue.

Para un demo público esto es, en parte, una **funcionalidad** (los evaluadores necesitan credenciales para entrar sin pedir un alta) y en parte un **riesgo** (esas contraseñas son públicas en el propio código fuente del repositorio, y con rol `ADMIN`/`OPERATOR` alcanzable desde cualquier IP). La solución no es desactivar el sembrado, sino dejar de tener las contraseñas fijas en el `.jar`: que el propio VPS pueda fijar las suyas.

## Alcance

- Externalizar las contraseñas semilla a variables de entorno (p. ej. `SEED_ADMIN_PASSWORD`, `SEED_OPERATOR_PASSWORD`, `SEED_MATH_PASSWORD`, `SEED_PLAYER_PASSWORD`), con los valores actuales como *default* **sólo quando no se definen** (para no romper el `docker-compose.yml` de desarrollo ni los tests/ITs existentes).
- Documentar en `.env.example` y `deploy/README.md` que el despliegue público debe fijar estas variables a valores propios (y que `scripts/smoke-test.sh` debe recibir la del jugador semilla para poder loguearse).
- No cambiar el resto del comportamiento de `SeedDataLoader` (usuarios/roles/idiomas).

## Criterios de aceptación (BDD)

```gherkin
# language: es
Característica: Contraseñas semilla configurables por entorno

  Escenario: Sin variables definidas (desarrollo local)
    Dado que no se definen las variables SEED_*_PASSWORD
    Cuando la aplicación siembra la base de datos vacía
    Entonces usa las contraseñas de desarrollo por defecto (como hoy)

  Escenario: Variables definidas (VPS del demo)
    Dado SEED_ADMIN_PASSWORD, SEED_OPERATOR_PASSWORD, SEED_MATH_PASSWORD y SEED_PLAYER_PASSWORD definidas
    Cuando la aplicación siembra la base de datos vacía
    Entonces cada cuenta semilla queda creada con la contraseña de su variable, no con el valor de desarrollo

  Escenario: El smoke test sigue funcionando
    Dado el VPS desplegado con sus propias contraseñas semilla
    Cuando scripts/smoke-test.sh recibe la contraseña del jugador semilla configurada
    Entonces el login del smoke test sigue pasando
```

## Verificación INVEST

| Criterio | Cumplimiento |
|---|---|
| **I**ndependiente | Cambia cómo se obtienen las contraseñas, no la lógica de sembrado. |
| **N**egociable | Nombres de las variables y si se agrupan en una sola vs. una por rol son negociables. |
| **V**aliosa | Mantiene el demo usable para evaluadores sin publicar contraseñas fijas del código fuente. |
| **E**stimable | Lectura de variables de entorno con *fallback* + actualizar el smoke test/documentación. |
| **S**mall | Acotada a `SeedDataLoader` y su documentación. |
| **T**estable | Test que verifica el uso del valor de entorno cuando está definido y el *default* cuando no. |

**Fuera de alcance:** eliminar el sembrado de cuentas demo (se necesita para el demo público) y gestión de secretos avanzada (ya cubierta por HU-24 para el resto de credenciales).
