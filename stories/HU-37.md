# HU-37 — Acotar la concurrencia de simulaciones para proteger el VPS del demo

> **Como** equipo de plataforma,
> **quiero** limitar cuántas simulaciones masivas se ejecutan a la vez,
> **para** que el VPS del demo (recursos modestos, no un clúster de producción) no se quede sin CPU/memoria si varias personas lanzan simulaciones grandes a la vez.

**Prioridad:** Should Have · **Estimación:** S/M · **Perfil:** Matemático/Plataforma

## Contexto y valor

`SimulationUseCase` valida bien `numSpins` (máx. 10M, readme §4.4.4), pero **no limita cuántas simulaciones corren en paralelo**. `SimulationExecutor.execute` está anotado `@Async` sin un `ThreadPoolTaskExecutor` propio configurado en el proyecto, por lo que Spring usa su executor por defecto (`SimpleAsyncTaskExecutor`, **sin límite de hilos**: crea uno nuevo por tarea). Cada simulación de varios millones de giros ya reparte trabajo entre todos los núcleos (el motor usa un `ForkJoinPool`); si dos o tres usuarios del demo lanzan simulaciones de 10M giros casi a la vez, el **VPS** (con recursos muy inferiores a un entorno de producción real) puede saturarse y afectar a quien esté usando el demo en ese momento — un auto-DoS accidental, no intencionado.

## Alcance

- Configurar un `ThreadPoolTaskExecutor` propio (con un tamaño de *pool* acotado, acorde a los núcleos del VPS) para el `@Async` de `SimulationExecutor`, en vez de depender del executor por defecto de Spring.
- Añadir un límite razonable de simulaciones **en curso** (global o por usuario) en `SimulationUseCase.launch`: si se supera, se rechaza con un error claro (p. ej. 429/`InvalidSimulationParamsException` específico) en vez de encolar sin límite.

## Criterios de aceptación (BDD)

```gherkin
# language: es
Característica: Concurrencia de simulaciones acotada

  Escenario: Simulaciones dentro del límite
    Dado menos simulaciones en curso que el límite configurado
    Cuando se lanza una nueva simulación válida
    Entonces se acepta y se ejecuta con normalidad

  Escenario: Se supera el límite de concurrencia
    Dado el número máximo de simulaciones en curso
    Cuando se intenta lanzar una simulación adicional
    Entonces la petición se rechaza con un error claro en vez de aceptarse sin control
```

## Verificación INVEST

| Criterio | Cumplimiento |
|---|---|
| **I**ndependiente | Un executor acotado + una comprobación en el caso de uso; no cambia el motor de simulación. |
| **N**egociable | El tamaño del *pool* y el límite de concurrencia son negociables (dependen del VPS elegido). |
| **V**aliosa | Evita que el demo se caiga por su propio uso normal. |
| **E**stimable | Un bean de executor + una comprobación de concurrencia + tests. |
| **S**mall | Acotada a la ejecución asíncrona de simulaciones. |
| **T**estable | Test que lanza más simulaciones que el límite y verifica el rechazo. |

**Fuera de alcance:** colas persistentes o *backpressure* distribuido (aplicable si se escalase a varios nodos, fuera del alcance de un demo en un único VPS).
