# HU-33 — Bug: `/actuator/health` exige autenticación y rompe el propio despliegue

> **Como** equipo de plataforma,
> **quiero** que el *healthcheck* de la API sea alcanzable sin autenticación,
> **para** que el contenedor `api` pueda declararse "healthy" y el despliegue (Docker Compose, CI/CD, *smoke test*) funcione tal y como está diseñado.

**Tipo:** Bug · **Prioridad:** Must Have · **Estimación:** S · **Perfil:** Plataforma/DevOps

## Síntoma

El propio despliegue documentado se rompe contra sí mismo: `deploy/docker-compose.prod.yml` define el *healthcheck* del servicio `api` como `wget -qO- http://localhost:8080/actuator/health`, y `scripts/smoke-test.sh` hace `curl .../actuator/health` esperando `"status":"UP"`. Verificado en vivo: **`GET /actuator/health` devuelve `401`**.

## Causa raíz

Doble, no sólo de seguridad:

1. **`spring-boot-starter-actuator` no era ni siquiera una dependencia del proyecto** (confirmado: ninguna referencia a "actuator" en todo el repositorio salvo la línea del *healthcheck* de `docker-compose.prod.yml`). El `/actuator/health` que el despliegue asume no existía como *endpoint* en absoluto.
2. Aun añadiéndolo, `SecurityConfig` (`backend/nova-web-api/.../config/SecurityConfig.java`) define la cadena de filtros con `.anyRequest().authenticated()` y **no** incluía ningún `permitAll()` para `/actuator/**`; Spring Security intercepta y devuelve `401` en su filtro, **antes** de que el *dispatcher* llegue a resolver si existe un controlador para esa ruta — de ahí que en la auditoría se observara un `401` y no un `404`.

Efecto en cadena: `docker compose up` nunca marca `api` como *healthy* → `web` (que depende de `api: condition: service_healthy`) **no llega a arrancar** → `deploy/deploy.sh` agota su bucle de espera y falla → `scripts/smoke-test.sh` falla en su primer chequeo → el paso de *rollback* de `cd.yml` se dispara en cualquier despliegue, incluido el primero.

## Corrección aplicada

- Añadida la dependencia `spring-boot-starter-actuator` a `nova-web-api`.
- `management.endpoints.web.exposure.include: health` (el valor por defecto de Spring Boot, dejado explícito) y `management.endpoint.health.show-details: never`: sólo se expone `/actuator/health` y sin detalles internos (nada de BBDD/disco/etc.), aunque sea público.
- Permitido sin autenticación **sólo** `/actuator/health/**` en `SecurityConfig`, manteniendo `anyRequest().authenticated()` para todo lo demás (por defecto, ningún otro *endpoint* de actuator queda expuesto vía web de todos modos).

## Criterios de aceptación (BDD)

```gherkin
# language: es
Característica: Healthcheck alcanzable sin autenticación

  Escenario: Comprobación de salud sin token
    Cuando se hace GET /actuator/health sin cabecera Authorization
    Entonces la respuesta es 200 con "status":"UP"

  Escenario: El resto de actuator sigue protegido
    Cuando se hace GET /actuator/env sin cabecera Authorization
    Entonces la respuesta NO es 200 (sigue exigiendo autenticación o no está expuesto)

  Escenario: El despliegue documentado funciona
    Dado deploy/docker-compose.prod.yml
    Cuando se levanta el stack
    Entonces el contenedor api alcanza el estado "healthy" y scripts/smoke-test.sh pasa su primer chequeo
```

## Verificación INVEST

| Criterio | Cumplimiento |
|---|---|
| **I**ndependiente | Un cambio acotado en `SecurityConfig`; no toca lógica de negocio. |
| **N**egociable | Qué sub-rutas de actuator quedan públicas (sólo health vs. health+info) es negociable. |
| **V**aliosa | Sin esto, **ningún** despliegue con el compose/CD documentados llega a arrancar. |
| **E**stimable | Un `permitAll` acotado + test. |
| **S**mall | Un fichero de configuración + su test. |
| **T**estable | IT que verifica 200 sin token en `/health` y que el resto de actuator sigue protegido. |

**Fuera de alcance:** exponer métricas/Prometheus o un puerto de gestión separado (ver backlog, fuera de este bloque).
