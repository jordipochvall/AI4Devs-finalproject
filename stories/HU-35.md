# HU-35 — El demo público sólo se sirve por HTTPS y la API no queda expuesta directamente

> **Como** equipo de plataforma,
> **quiero** que el VPS sólo acepte tráfico HTTPS por el proxy web y que la API no sea alcanzable directamente desde internet,
> **para** proteger las credenciales y la sesión de quien pruebe el demo público y reducir la superficie de ataque.

**Prioridad:** Must Have · **Estimación:** S/M · **Perfil:** Plataforma/DevOps · **Endpoint:** *(infra/red, sin endpoint)*

## Contexto y valor

El demo se va a exponer en un **VPS con acceso público** (no es producción real, pero sí es internet abierto). Dos huecos concretos encontrados en la auditoría:

- **Sin TLS.** `frontend/nginx.conf` sólo escucha en `:80`. En un VPS público, servir login/JWT en claro por HTTP es evitable con un esfuerzo pequeño (hoy en día además muchos navegadores avisan de "sitio no seguro").
- **La API se publica dos veces.** `deploy/docker-compose.prod.yml` mapea `api` con `ports: ["8080:8080"]` **además** de que `web` ya hace de proxy inverso hacia `http://api:8080/api/` (`nginx.conf`). Eso dobla la superficie expuesta: cualquiera en internet puede hablar con Spring Boot (y su Swagger/actuator) directamente en el puerto 8080, saltándose el único punto de entrada pensado (`web`).

## Alcance

- Añadir terminación TLS delante de `web` (por ejemplo, Caddy o nginx+certbot con renovación automática) usando el dominio/subdominio del VPS; redirigir `:80` → `:443`.
- Quitar el mapeo `ports: ["8080:8080"]` de `api` en `docker-compose.prod.yml`: la API queda **sólo** en la red interna de Compose, alcanzable únicamente a través de `web`.
- Mantener el *healthcheck* interno de `api` (usa `localhost:8080` dentro del propio contenedor, no depende del puerto publicado).

## Criterios de aceptación (BDD)

```gherkin
# language: es
Característica: Sólo HTTPS y API no expuesta directamente

  Escenario: Acceso por HTTP se redirige
    Cuando alguien visita http://<dominio-del-vps>
    Entonces es redirigido a https://<dominio-del-vps>

  Escenario: La API no es alcanzable en el puerto 8080 desde fuera
    Cuando alguien intenta conectar a <ip-del-vps>:8080 desde fuera del VPS
    Entonces la conexión no se establece (puerto no publicado)

  Escenario: El healthcheck interno sigue funcionando
    Dado el stack desplegado
    Cuando Docker evalúa el healthcheck de "api"
    Entonces sigue reportando "healthy" (usa la red interna, no el puerto publicado)
```

## Verificación INVEST

| Criterio | Cumplimiento |
|---|---|
| **I**ndependiente | Cambios en `docker-compose.prod.yml` y el proxy; no toca la aplicación. |
| **N**egociable | La herramienta de TLS (Caddy vs. nginx+certbot) es negociable. |
| **V**aliosa | Evita servir credenciales/JWT en claro y cierra una vía de acceso directo a la API. |
| **E**stimable | Configuración de proxy + certificado + un cambio de una línea en el compose. |
| **S**mall | Puramente de infraestructura/despliegue. |
| **T**estable | Redirección HTTP→HTTPS y puerto 8080 cerrado, verificables desde fuera del VPS. |

**Fuera de alcance:** WAF, CDN o mitigación de DDoS (no aplica a un demo de proyecto final).
