# HU-34 — Versionar y activar el pipeline de CI/CD para poder desplegar al VPS

> **Como** equipo de plataforma,
> **quiero** que los *workflows* de CI/CD estén versionados en el repositorio y el entorno de destino configurado,
> **para** poder construir, publicar y desplegar la aplicación a un servidor real en lugar de hacerlo manualmente.

**Prioridad:** Should Have · **Estimación:** S · **Perfil:** Plataforma/DevOps · **Endpoint:** *(infra/CI-CD, sin endpoint)*

## Contexto y valor

`HU-24` ya diseñó e implementó el pipeline de entrega continua (`.github/workflows/ci.yml`, `cd.yml`, `deploy/`, `scripts/smoke-test.sh`): construcción de imágenes versionadas, despliegue a *staging*, promoción a producción con aprobación manual y *rollback*. Sin embargo, **el directorio `.github/` nunca se ha comprometido al repositorio** (`git status` lo marca como no *trackeado*): los *workflows* existen en disco pero GitHub Actions no los ejecuta en ningún *push* ni *pull request*, y no hay ningún entorno (*Environment*) configurado con los secretos del VPS de destino. Sin este paso, cualquier despliegue tendría que hacerse a mano.

## Alcance

- Comprometer `.github/workflows/ci.yml` y `.github/workflows/cd.yml` (y cualquier fichero auxiliar de `.github/`) al repositorio.
- Verificar que `ci.yml` corre en el siguiente *push*/PR (build+test backend y frontend, JaCoCo, *perf job*).
- Configurar en GitHub el *Environment* `production` (o el nombre que se use para el VPS) con **required reviewers** y los secretos que `cd.yml` espera: `*_DB_URL`, `*_DB_USER`, `*_DB_PASSWORD`, `*_JWT_SECRET`, `*_ANTHROPIC_API_KEY`, `*_BASE_URL`.
- Documentar en `deploy/README.md` cómo apunta ese entorno al VPS concreto (IP/dominio, usuario de despliegue).

## Criterios de aceptación (BDD)

```gherkin
# language: es
Característica: Pipeline de CI/CD operativo

  Escenario: CI corre en el repositorio remoto
    Dado un push a una rama con PR abierta
    Cuando GitHub Actions evalúa el repositorio
    Entonces el workflow "CI" se ejecuta y publica sus resultados (tests + cobertura)

  Escenario: CD puede desplegar al VPS
    Dado el Environment "production" configurado con sus secretos
    Cuando se aprueba una promoción a producción
    Entonces deploy.sh se ejecuta contra el VPS de destino con las credenciales correctas
```

## Verificación INVEST

| Criterio | Cumplimiento |
|---|---|
| **I**ndependiente | Cambio de repositorio/configuración de GitHub; no toca código de la aplicación. |
| **N**egociable | El nombre del *Environment* y el proveedor del VPS son negociables. |
| **V**aliosa | Sin esto, cada despliegue al VPS sería manual y no repetible. |
| **E**stimable | Comprometer ficheros + configurar *Environment* + verificar una corrida. |
| **S**mall | Es de configuración, no de código. |
| **T**estable | Una corrida verde de CI y un despliegue de CD que llega al VPS. |

**Fuera de alcance:** cambiar el diseño del pipeline (ya definido en HU-24); multi-región o autoescalado.
