# HU-25 — Gestión multi-operador (super-admin)

> **Como** administrador de la plataforma,
> **quiero** dar de alta y gestionar varios operadores con sus datos aislados,
> **para** explotar comercialmente el modelo B2B multi-tenant que el esquema ya soporta.

**Contexto y valor.** El modelo de datos es multi-tenant (`operators` como raíz), pero el MVP opera con un **único operador semilla**. Esta historia introduce el rol `ADMIN` y las operaciones de alta/gestión de operadores, garantizando el **aislamiento estricto** de datos entre tenants (jugadores, juegos, partidas, simulaciones).

> **Nota técnica.** El rol `ADMIN` **no existe** en el dominio actual de `users.role` (CHECK `PLAYER`/`OPERATOR`/`MATH_ANALYST`, §3.2.12); esta historia requiere una **migración Flyway** que amplíe la constraint `CHECK` y la autorización por rol en la seguridad. Es un cambio aditivo sin impacto en los datos existentes.

**Prioridad:** Could Have · **Estimación:** M · **Endpoint:** `GET /admin/operators` · `POST /admin/operators` *(nuevos)*

## Criterios de aceptación (BDD)

```gherkin
# language: es
Característica: Gestión multi-operador

  Antecedentes:
    Dado un administrador de plataforma autenticado

  Escenario: Alta de un nuevo operador
    Cuando doy de alta un operador con su usuario operador inicial
    Entonces el operador queda creado y activo
    Y su usuario operador puede iniciar sesión sobre datos vacíos y aislados

  Escenario: Aislamiento entre operadores
    Dado dos operadores con actividad
    Cuando un operador consulta jugadores, partidas o simulaciones
    Entonces nunca ve datos del otro operador

  Escenario: Activar/desactivar un operador
    Cuando desactivo un operador
    Entonces sus usuarios no pueden operar hasta su reactivación

  Escenario: Solo el administrador
    Cuando un rol distinto de administrador accede a la gestión de operadores
    Entonces se rechaza con "acceso denegado"
```

## Verificación INVEST

| Criterio | Cumplimiento |
|---|---|
| **I**ndependiente | Se apoya en auth/roles (HU-4); el aislamiento por `operator_id` ya está en el modelo. |
| **N**egociable | El alcance de la administración (cuotas, branding por tenant) es negociable. |
| **V**aliosa | Convierte el producto en una plataforma B2B real con varios clientes. |
| **E**stimable | Rol `ADMIN` + endpoints de alta/gestión + verificación sistemática de aislamiento. |
| **S**mall | Es **M**: el alta básica primero; cuotas y personalización por tenant después. |
| **T**estable | Verificable con dos operadores y aserciones de no-fuga de datos entre ellos. |

**Fuera de alcance:** facturación por operador, *branding*/temas por tenant y límites de uso (cuotas) por operador.
